# Dynamic Horizontal Partitioning — Development Plan

**Status:** v2, self-reviewed (see Log). Tracked live — update checkboxes and log entries as work lands, same convention as `write-routing-and-term-authority-progress.md`. No implementation has started; this is a research + planning deliverable.

**Goal (verbatim from the user):** move away from a fixed shard count decided at index creation, toward genuinely dynamic, horizontally-scaling partitioning — inspired by how S3, DynamoDB, and Cassandra scale, and specifically asked to assess Vespa. Deep code research + external-system research first, feasibility verdict, then a phased plan.

**Verdict up front: feasible, and cheaper than it looks — for a reason unique to this fork's current moment.** Upstream OpenSearch core (this very fork, merged March–June 2026, PRs #20859/#20979/#21120) has landed the hardest, most foundational piece of a DynamoDB-style dynamic-shard-count design — an **unbounded hash-range split** data model — but left it almost entirely unwired (no REST API, no allocation-service integration, no recovery implementation). This plugin *also* already has a zero-copy, manifest-based split mechanism (`ShardSplitter`/`ShardCloner`) built for an unrelated reason (avoiding a real Lucene segment copy). The plan below is fundamentally about **connecting these two existing, independently-built pieces** rather than building a dynamic-partitioning system from scratch inside the plugin, which was the assumption this investigation started with and turned out to be wrong.

## Part 1: What "dynamic horizontal scaling" means in each reference system

Condensed from deep research (full agent transcripts available in this session's history; citations preserved here for the load-bearing claims).

### DynamoDB — the closest match to the goal
- Hash-then-**range**-split, not consistent hashing: partition key → MD5 (128-bit) → each partition owns a disjoint, contiguous slice of that hash number line. A split picks a new split point and divides one slice in two — architecturally a B-tree/index-page split over hash values.
- Triggers: **split-for-size** (hard 10GB partition limit) and **split-for-heat** (sustained throughput near capacity), the latter splitting at a point chosen from recent traffic to spread heat evenly.
- **The mechanism that actually makes it work**: a **metadata-lookup routing layer**, not a static routing table. Request Routers consult a distributed metadata cache (MemDS) to map key → current partition; when a partition splits, new split-point + replication-group metadata propagates to routers, and the client's next request for that key just resolves differently. The client and the routing table never encode a partition *count* at all.
- Splits are made **locally** by storage nodes monitoring their own utilization; Global Admission Control (a distributed token-bucket service) proactively triggers splits/relocations before throttling. The precise in-flight-write cutover protocol during a split is not publicly documented in enough detail to cite with confidence — treat as an open engineering question even for DynamoDB-inspired designs, not a solved recipe to copy verbatim.
- Source: 2022 USENIX ATC paper ("Amazon DynamoDB: A Scalable, Predictably Performant, Fully Managed NoSQL Database Service"), AWS's own "split-for-heat" blog series, Marc Brooker's engineering blog.

### Cassandra — dynamic *placement*, not dynamic *partition count*
- Vnodes: each physical node owns many small, non-contiguous token ranges instead of one big arc, so adding/removing a node touches many current owners at once instead of overloading one neighbor — ~1/N of total data moves on a node join, not a full-cluster reshuffle.
- **Critical finding directly answering the question this research started with**: vnode granularity (`num_tokens`) is fixed at cluster bootstrap and can never be changed after a node joins ("the node will fail on restart" if changed). Cassandra has **no notion of splitting an individual partition** because it grew hot or large — the scaling unit is strictly whole-node add/remove; token ranges are *reassigned*, never subdivided. An oversized partition stays whole (a documented Cassandra anti-pattern).
- Relevance to us: Cassandra's model answers a different problem than the one in this goal (rebalancing *ownership* across nodes, which this plugin already has via `ServerlessStorageExistingShardsAllocator`) — not "a partition grew too big, split it," which is the actual ask. Cassandra is the wrong model to imitate for partition-count dynamism; it's a reasonable model to imitate for placement/gossip if we ever outgrow cluster-state-based allocation (out of scope here).

### Vespa — the most sophisticated model, and structurally why
- Documents hash (MD5) into a 58-bit "location"; a cluster-state "distribution bit count" determines how many LSBs form a **bucket**. Buckets **split when they grow too big and join when they shrink** ([docs.vespa.ai/en/content/buckets.html](https://docs.vespa.ai/en/content/buckets.html)) — independent of node-count changes. This is Vespa's DynamoDB-like axis.
- Node placement is a *separate* axis: an **ideal-state algorithm** (Vespa's own docs call it "weighted random election," described elsewhere as CRUSH-like) deterministically computes, per bucket, which node should hold it — seeded by the bucket ID, no coordination needed. Adding a node makes it win ~1/n of buckets *without moving any data between the pre-existing nodes* — strictly better than Cassandra's model, where existing nodes still shuffle ranges among themselves.
- **Why Vespa can do both axes and Lucene-based systems can't**: Vespa's per-node engine (Proton) is built around the bucket abstraction from the ground up — bucket management, and a ready/not-ready/removed sub-DB split per bucket, are native concepts. There is no "one Lucene index == one shard, segment-per-shard" coupling the way OpenSearch/Elasticsearch shards work. This is the single most important transferable insight from the Vespa research: **the reason Vespa's model is hard to retrofit onto OpenSearch core is that core's shard concept is inseparable from "one whole Lucene index."** Anything we build has to either work around that coupling or accept it as a hard constraint at some layer.
- Real (if narrow) engineering numbers: a 2022 Vespa blog on redistribution throughput (12 nodes, 230M docs, 311GB) reports node-replacement redistribution improved from ~22.5MB/s to ~44MB/s, cutting one replacement from ~3h50m to ~2h. Useful as an order-of-magnitude sanity check, not a general benchmark.

### S3 — the narrowest, and the most directly relevant to *our* architecture
- Range-based (not hash-based) split of a **sorted key-metadata index**, confirmed by AWS's own blog: "S3 supports a lexicographically-sorted list API, [so] the key names themselves are used… in both the map and the partitioning scheme," and S3 "attempts to find an optimal spot along the full key to split a given dataset into two partitions."
- **The core insight, and the one that matters most for us**: S3 decouples a small, range-splittable **key/metadata index layer** from the **blob storage layer**, which is keyed by opaque UUIDs and is therefore uniformly distributed and trivially horizontally scalable by construction — it never needs partitioning logic at all. Sharding "the metadata index" is a much narrower problem than sharding a whole search index (no inverted indices, aggregations, or cross-shard scatter/gather beyond a prefix `LIST`).
- **This maps almost exactly onto what this plugin already has.** Our bundle files (the actual segment bytes in the object store) are already content-addressed/generation-keyed and require zero partitioning logic to scale — they're already the S3 "blob layer." The thing that currently has a fixed count is the **manifest/routing layer** — one `CommitManifest`/`ShardHead` per real core `ShardId`, one blob-path prefix (`<indexUuid>/<shardId>`) per shard. That is exactly S3's "key index," and it's exactly the layer DynamoDB and Vespa also treat as the one that needs dynamic partitioning. Three independent systems converge on the same architectural shape; we already have half of it.

### Prior art in Lucene-based search engines — nobody has shipped this, with one partial exception
- **Elastic Cloud Serverless "autosharding"**: confirmed via Elastic's own blog — only sets shard count for the **next** backing index at rollover. Never re-shards a live, already-written index. Their "stateless" architecture (object store as source of truth, thin relocatable shards) makes shards *cheap to move*, but does not remove the fixed-shard-count-per-index assumption; repartitioning still rides on rollover. (This matches and confirms our own earlier session's Part-2 finding when we built the equivalent feature for data streams.)
- **SolrCloud `SPLITSHARD`** is the closest real precedent: genuinely splits an **active**, write-receiving shard with no downtime — sub-shards start in `CONSTRUCTION`, buffer in-flight updates in their own update log while the parent keeps serving, then flip to `ACTIVE` while the parent goes `INACTIVE` and is later cleaned up. But it does this by physically dividing the parent's **Lucene index** into sub-shard indexes by hash range (a real segment rewrite), and it's documented as operationally fragile (shards can get stuck `down` on failure). This is the one system that proves "live split without new-collection" is *possible* on top of Lucene, at the cost of a real data copy and real operational risk.
- **Amazon OpenSearch Serverless**: shard count is not user-modifiable and is chosen by the service; recent work adds *replica* scaling under query load, not primary-shard splitting.
- **Conclusion**: the specific gap — routing-only resharding over a fine object-store partition scheme on *live* Lucene-shard data, without a segment rewrite — is real, unclaimed whitespace. Nobody has built it. This plan is proposing to build something genuinely new, not catch up to a solved problem.

## Part 2: What we actually have today (grounded in this session's own code, verified by direct reads, not just agent summaries)

### 2a. Classic OpenSearch core `_split`/`_shrink` — the old, capped mechanism
- `numberOfShards` is a scalar on `IndexMetadata`, assumed immutable everywhere it's read (`IndexMetadata.java:1213,1491,2311,2420` — assertions and loops sized to it).
- The routing formula (`OperationRouting.generateShardId`, `OperationRouting.java:512-565`) is `floorMod(Murmur3Hash(routingValue), routingNumShards) / routingFactor`. `routingNumShards` is an over-provisioned hash space fixed at index-creation time specifically so `_split` can later reassign contiguous sub-ranges without rehashing — this is core's original (2017-era) concession to future resharding flexibility.
- **The hard cap**: `MetadataCreateIndexService.calculateNumRoutingShards` caps `routingNumShards` at **1024**, meaning a 1-shard index using the classic mechanism can be split at most **10 times total, ever** (2^10 = 1024), decided irrevocably at creation time. This is nothing like DynamoDB's effectively-unbounded 128-bit hash space.
- Classic `_split`/`_shrink` always creates a **brand-new index** and copies data — this is the mechanism this plugin's own `ProvisionSplitTargetsAction`/`ShardSplitter`/`OrchestrateShardSplitAction` (built in earlier sessions) mirrors, deliberately, because it's the only sanctioned core contract to build against at the time.

### 2b. NEW (this fork, real, unfinished, `@ExperimentalApi`) — in-place split scaffolding
Landed via real upstream PRs on this branch's history (`ed2e1006639` #20859 Mar 18 2026, `f716dfcdca1` #20979 Apr 1 2026, `0f58cfff8fa` #21120 Apr 5 2026), gated `Version.V_3_7_0`+:

- **`SplitShardsMetadata`/`ShardRange`** (`server/src/main/java/org/opensearch/cluster/metadata/`): a genuinely different, **unbounded** hash-range split model, independent of `routingNumShards`/1024. Verified directly: `SplitShardsMetadata.Builder.splitShard(shardId, numberOfChildren)` divides a parent's `[start, end]` range (full 32-bit `int` space, `Integer.MIN_VALUE`..`Integer.MAX_VALUE`) into N children, refusing only when the resulting range would fall below `MINIMUM_RANGE_LENGTH_THRESHOLD = 1000` — i.e., a single starting shard can be split roughly 4.3 million ways before hitting the floor. This is architecturally the same idea as DynamoDB's hash-range B-tree split, already built, already unbounded.
- **`OperationRouting.generateShardId`** already resolves through this: `indexMetadata.getSplitShardsMetadata().getShardIdOfHash(rootShardId, hash, includeInProgressChild)` (`OperationRouting.java:565`) binary-searches the current `ShardRange[]` to find the owning child. This is exactly the routing-indirection property that keeps already-indexed documents reachable across a split — the single hardest correctness property any of these systems needs, and it's done.
- **`MetadataInPlaceSplitShardService`** mutates `IndexMetadata`'s new split-tracking fields and triggers a reroute — but confirmed via direct grep: **zero references** to `SplitShardsMetadata`/`isSplitTarget`/`SPLITTING` anywhere in `AllocationService`, `RoutingTable`, or `IndexRoutingTable`. The cluster-manager-side data model exists; nothing turns a recorded split into real new `ShardRouting` entries with shard copies actually being allocated to nodes.
- **`ShardRouting.isSplitTarget()`/`getParentShardId()`/`getRecoveringChildShards()`** and `RecoverySource.InPlaceSplitShardRecoverySource` exist as types. `ShardRoutingState.SPLITTING` was added to the "active" state set (so a splitting shard doesn't read as unassigned/red). But **zero references** to any of this in `IndexShard.java` — no actual recovery implementation consumes `InPlaceSplitShardRecoverySource` to perform a real split-and-copy.
- **No REST or transport action exists** to trigger any of this — only an internal `InPlaceSplitShardClusterStateUpdateRequest` class, no public API surface.
- **No merge/shrink-in-place counterpart exists at all** — this scaffolding is split-only.

**Bottom line on 2b**: this is a partially-built skeleton with the two hardest, most foundational pieces done (an unbounded hash-range data model, and the routing-formula indirection to keep it correct) and the mechanically bulkiest pieces (allocation wiring, a real recovery implementation, a public API, a trigger policy) not started. This is unusual, valuable timing — building on top of this is materially less work than building an equivalent routing layer from scratch inside the plugin, which was this investigation's original assumption.

### 2c. This plugin's own manifest/zero-copy split machinery — already built, already the right shape for 2b's missing recovery piece
- `ShardSplitter.split` / `ShardCloner.clone` (`plugins/serverless-storage/.../resharding/ShardSplitter.java`, `.../clone/ShardCloner.java`): creates a target shard identity that references the *exact same* source-generation bundle files (zero-copy — no segment bytes actually move), plus a `ShardPartitionDescriptor` recording which hash partition the target serves. `PartitionFilteringDirectoryReader` makes each target's Lucene reads return only its own slice of the shared, unpartitioned bundle files.
- This is **not currently wired to core's routing formula at all** — it requires a real, separately-provisioned core `ShardId`/index (via `ProvisionSplitTargetsAction`) and core's own alias-based `CutoverSplitRoutingAction`/`WritePartitionRoutingActionFilter` to redirect traffic, because it was built against the *classic* "new index" contract, the only one that existed when it was built.
- **The key realization this plan is built on**: `ShardSplitter.split`'s actual work — "create a new shard identity that logically owns a hash sub-range of an existing shard's data, without copying bytes, with a reader-side filter enforcing the boundary" — is *exactly* what `InPlaceSplitShardRecoverySource` needs a real implementation to do. We already built the data-movement primitive core's new scaffold is missing. We built it for the wrong API contract (new-index) by necessity, and now have a better one to retarget it at.
- One real constraint to carry forward honestly: `ShardPartitionDescriptor`'s own javadoc currently states "a shard's partition assignment never changes across its own lifetime... a further split would create new target shards of its own" — this was written under the *classic* "split = new index" assumption. Under an in-place model, a shard's partition assignment **must** be able to change (a child can itself later become a parent). This is a real, scoped code change, not just a doc update — flagged explicitly in Phase 2 below.

### 2d. Reconciling with `OrchestrateShardSplitAction` (this session's own earlier work)
The classic "create a new index and copy" split mechanism (`ProvisionSplitTargetsAction`/`ShardSplitter`/`OrchestrateShardSplitAction`, built earlier in this same session) does not become dead code once this plan's in-place mechanism lands, and should not be deprecated by default:
- It remains the only option when an operator genuinely wants a **different index** (different settings, a deliberate re-mapping, a version upgrade path) — in-place split by definition cannot change anything about the shard except its hash-range ownership.
- It remains the fallback for indices where `SplitShardsMetadata`'s in-place model doesn't apply for some reason not yet discovered.
- **Decision for this plan**: keep both, clearly documented as separate tools for separate jobs (matches this plugin's existing "narrow, composable primitives" philosophy) — do not attempt to unify them into one API. Revisit only if real operational experience shows the two paths cause operator confusion.

## Part 3: Correctness questions a "very detailed" plan cannot leave implicit

These are read/replica/durability interactions the phased plan above depends on getting right in Phase 0, called out separately because they're easy to gloss over at the "write a manifest, don't copy bytes" level of description above.

- **Read-path correctness during the split transition window.** Once a child gets a real `ShardRouting` entry (Phase 0.2), core's ordinary "fan out to every active shard in the routing table" search behavior should naturally pick it up — but the transition has a real window where the parent is still `STARTED`-serving-everything while a child is `SPLITTING`/recovering. A search hitting both parent and a partially-ready child risks double-counting documents that exist in both (the child's manifest, until physical rewrite happens, references the *same* underlying bundle files the parent does — this plugin's own "logical-first, physical-later" split model, reused deliberately from Phase 0.4). **This needs an explicit answer, not an assumption**: either (a) a splitting child must not become search-visible until the split fully commits and the parent atomically stops being search-visible for that hash range in the same cluster-state update (the safer, DynamoDB-like option — a partition is owned by exactly one visible node at a time, even mid-split), or (b) some other de-duplication mechanism. Resolve this as part of Phase 0.1/0.2's design, before writing 0.3/0.4 — it's a correctness property, not an optimization.
- **Replica coordination.** If the shard being split has replica copies (this session's B12/B13 work specifically built and tested writer-replica live promotion), does each replica independently apply the same `SplitShardsMetadata` transition and derive the same children, or does the primary's split get replicated to followers explicitly? Core's own scaffold doesn't yet answer this (no `AllocationService` wiring exists at all yet, per 2b) — Phase 0.2's design must cover the replica case, not just the 0-replica case, learning from this session's own finding that the 0-replica and >0-replica cases needed genuinely different reasoning for B8.
- **WAL/term-authority interaction.** This plugin's WAL mirroring (`WalChunkService`, `ObjectStoreWriterEngine#activationWalPosition`, the B1-B13 term-authority-fencing work from earlier this session) is currently modeled as one continuous per-`ShardId` stream. A live split needs an explicit answer for what happens to WAL replay/fencing state across the split boundary: does each child inherit a read-only view of the parent's WAL history up to the split point, forever, or does WAL mirroring itself need to become partition-aware? This is a real dependency on prior work in this same session, not a new independent concern — flag it for Phase 0.1's design reading, and do not assume it's automatically fine just because bundle files are shared.

## Part 4: The core architectural decision

**Do not build a new dynamic-partitioning system inside the plugin from scratch.** Complete core's own nascent, unbounded, `@ExperimentalApi` in-place-split scaffold (2b), using this plugin's own zero-copy manifest split (2c) as the actual data-movement implementation behind `InPlaceSplitShardRecoverySource`, instead of a real Lucene segment copy the way classic Lucene-based recovery would otherwise require.

This gives us, for the first time among Lucene-based systems investigated (Elasticsearch, OpenSearch classic, Elastic Serverless, SolrCloud, Amazon OpenSearch Serverless):
- **Unbounded** partition count per original shard (no 1024 cap), matching DynamoDB's architecture.
- **Routing-only** resharding — no segment rewrite, because our real data already lives in immutable, content-addressed object-store bundles the way S3's blob layer does; "splitting" only ever means writing a new manifest + partition descriptor, never copying bytes. This is *cheaper* than DynamoDB's own split (which does copy the underlying B-tree data) and categorically different from Solr's `SPLITSHARD` (which does a real segment rewrite).
- A real shot at **live**, already-receiving-writes shard splitting without a new index/reindex, closing the one gap every other Lucene-based system (including our own earlier `OrchestrateShardSplitAction` work this session) has left open.

What this does **not** give us, and what stays honestly out of scope for this plan (see Part 6): Vespa-style node-count elasticity independent of partition count (its "steal 1/n of buckets from every node, move data only into the new node" property), a distributed metadata-lookup routing service independent of cluster state (DynamoDB's MemDS — core's routing indirection is resolved locally from cluster state on every node, which is simpler and consistent with how OpenSearch already works, but doesn't have MemDS's separately-scalable properties), and in-place **merge/shrink** (no core scaffold for this exists at all yet).

**Scale expectations, stated plainly.** Phase 0 alone — and specifically item 0.2, wiring `AllocationService`/`RoutingTable` to actually allocate real shard copies for an in-place split — is core, shared, every-shard-in-the-cluster machinery with a materially larger blast radius than any single change made in this session (larger than B8's `Engine#onPrimaryTermBumped` hook, which itself was flagged and reviewed carefully before being written). This is not a "few sessions" project. Treat Phase 0 as the work of a genuine feature effort with its own design-review checkpoints, not a checklist to move through at this session's usual pace. The rest of this plan (Phases 1-3) is comparatively incremental once Phase 0 is real and tested — the correct place to be conservative and slow is Phase 0, not later.

## Part 5: Phased development plan

Each phase should land as its own reviewed, tested, committed increment — same discipline as the rest of this session's work (implement → real test → verify meaningfulness by breaking it → full plugin quality gate → full `internalClusterTest` sweep → progress-doc update → commit → push). Phases are ordered by dependency, not strictly by calendar; some sub-items can run in parallel once their prerequisites land.

### Phase 0 — Prove the concept end-to-end at the smallest possible scope
Goal: one real, live, in-place split of a real serverless-storage shard, triggered manually, with zero data loss and continued read/write availability — no automation, no policy, no merge. This phase exists to de-risk the big unknown (does wiring our zero-copy manifest split behind core's `InPlaceSplitShardRecoverySource` actually work end-to-end) before investing in automation on top of it.

- [ ] **0.1** Read `MetadataInPlaceSplitShardService`, `InPlaceSplitShardClusterStateUpdateRequest`, and the `SplitShardsMetadataTests`/`ShardRangeTests` test suites in full (not just the summary above) to understand the exact cluster-state transition sequence a split goes through today, and what "parent" vs "in-progress child" vs "committed child" state transitions look like.
- [ ] **0.2** Design and add the missing `AllocationService`/`RoutingTable` wiring: when `SplitShardsMetadata` records an in-progress split, `IndexRoutingTable`/`RoutingNodes` must gain real `ShardRouting` entries for the child shard IDs, in `SPLITTING` state, with `getParentShardId()` pointing at the source. This is real core-surface work with a large blast radius (shared allocation machinery) — same caution level as this session's B8 core hook: ground every claim in the actual allocation code before writing it, and expect this to need the most careful review of any item in this plan.
- [ ] **0.3** Implement `InPlaceSplitShardRecoverySource` handling in `IndexShard`/`RecoveryTarget`/`StoreRecovery` (wherever core dispatches on `RecoverySource` type) that, for a `ServerlessStorageIndexSettingProvider`-enabled index, delegates to a new plugin-side hook rather than doing a real local segment copy — the seam should be similar in shape to this session's `Engine#onPrimaryTermBumped` hook (small, no-op-by-default, narrowly scoped).
- [ ] **0.4** In the plugin, implement that hook by adapting `ShardSplitter.split`/`ShardCloner.clone` to write directly into the **same core `ShardId`'s** manifest history (not a new index/UUID) — i.e., the child's object-store identity becomes a partition-scoped sub-path or a partition-tagged manifest under the *parent's original* blob-path prefix, not `ProvisionSplitTargetsAction`'s current "brand-new indexUuid" model. This is the piece that needs the most new design: today `<indexUuid>/<shardId>` is a flat, 1:1 path; a real in-place child needs its own manifest identity while still being addressable from the same core `ShardId` once promoted. Candidate shapes to evaluate: (a) child manifests live under a synthetic sub-`ShardId` derived deterministically from `(parentShardId, ShardRange)`, later renamed/promoted once the split commits; (b) a new blob-path segment, e.g. `<indexUuid>/<shardId>/<generation-or-range-tag>/`, decided once and cheap to reference from `ShardHead`. Do not guess this in isolation — treat it as its own short design spike with a written decision before implementation, since it's the one piece with no precedent in either core's scaffold or this plugin's existing code.
- [ ] **0.5** Update `ShardPartitionDescriptor`'s contract (and its javadoc, which currently asserts partition assignment is lifetime-immutable) to allow a child to later become a parent of a further split. Audit every existing caller of `ShardPartitionDescriptor`/`PartitionFilteringDirectoryReader` for that assumption.
- [ ] **0.6** REST/transport action to trigger an in-place split manually (operator-only at this phase, mirroring `ProvisionSplitTargetsAction`'s "operator always supplies the split, no invented policy" discipline this session established) — this also closes core's own missing public-API gap from 2b.
- [ ] **0.7** IT: real 2-node cluster, real writer index, index+flush some docs, trigger an in-place split via the new REST action, assert (a) the shard never leaves the routing table / never goes red, (b) reads/writes against both the original alias and post-split routing continue succeeding throughout, (c) every pre-split document is reachable post-split via the correct child using `OperationRouting`'s real hash resolution (not a plugin-side reimplementation of routing), (d) no bundle bytes were physically copied (assert via object-store request-count metrics, §18 risk #1's existing signal, that a split does not trigger a bulk copy).
- [ ] **0.8** Full quality gate + full `internalClusterTest` sweep + a matching core-level test sweep (this touches `AllocationService`/`IndexShard`, so the same "run the full existing suite, not just new tests" discipline B8 used applies here, at larger scope — expect to need `server:test` sweeps beyond just `IndexShardTests`).

### Phase 1 — Automatic split triggering (the DynamoDB "split-for-size"/"split-for-heat" policy layer)
Goal: turn Phase 0's manual REST trigger into a policy-driven controller, reusing signals this plugin already has.

- [ ] **1.1** Extend `ShardSplitCandidatesAction`'s existing `writesPerMinute()`-based signal (already built, already advisory-only, already has threshold + sustained-duration hysteresis) to also track shard *size* (bundle byte count from existing manifest/cost-accounting metrics), giving both a DynamoDB-style split-for-size and split-for-heat trigger.
- [ ] **1.2** New scheduler task (same shape as `DataStreamShardCountAdvisorSchedulerTask` from this session's earlier work) that periodically evaluates candidates and calls the Phase 0 in-place-split action automatically, gated behind a disabled-by-default node setting exactly like every other autoscaling signal in this plugin.
- [ ] **1.3** Split-point selection policy: for split-for-size, a simple midpoint bisection of the current `ShardRange` is sufficient (matches core's own `splitShard(shardId, numberOfChildren)` default shape). For split-for-heat, evaluate whether a cheap approximation of "which sub-range is actually hot" is feasible given what signals we already collect, or whether hysteresis alone (wait, re-measure after split) is an acceptable first cut — DynamoDB's own real split-point-for-heat algorithm is not confidently documented publicly (see Part 1), so don't over-invest in matching it exactly; a simpler first version that's honest about its limits is preferable to guessing at an undocumented algorithm.
- [ ] **1.4** Same "no silent, invented policy" review discipline this whole session has applied — cooldown/hysteresis constants should be flagged as illustrative/untuned against real workload, exactly as `ShardSplitCandidatesAction`'s existing threshold already is.

### Phase 2 — Merge (the missing "join" — Vespa's other half, and Cassandra-style consolidation for shrunk workloads)
Goal: the inverse of Phase 0/1 — when two sibling partitions (or a shard's overall write/query rate) shrink enough, merge them back down, since dynamic scaling that only ever grows isn't dynamic scaling.

- [ ] **2.1** Core has **no** in-place merge/shrink scaffold at all (confirmed — the new `SplitShardsMetadata`/`ShardRange` model is split-only). This phase requires designing the inverse data model from scratch: which cluster-state transitions retire two `ShardRange`s back into one, how `OperationRouting.getShardIdOfHash` should degrade gracefully if it's ever asked to resolve a hash whose owning range was just merged away, and what the recovery-source equivalent of `InPlaceSplitShardRecoverySource` looks like for a merge (a shard adopting a sibling's `ShardRange` and manifest history rather than the reverse).
- [ ] **2.2** This plugin already has a real, tested, Lucene-merge-based `ShardShrinker` (built in an earlier session) — evaluate whether its physical-merge approach is reusable for in-place merge, or whether (matching the split side's insight) merge should also be a manifest-level operation (union two partition filters, no physical merge) until/unless a physical compaction is separately triggered by `PartitionRewriteSchedulerTask` (which already exists for exactly this "logical-first, physical-later" purpose on the split side).
- [ ] **2.3** Merge trigger policy: sustained-low-activity signal on adjacent sibling shards, mirroring the scale-to-zero suspend/reactivate machinery this plugin already has (`ShardSuspensionCoordinator`, `SuspendedShardsMetadata`) rather than inventing a new signal shape.
- [ ] **2.4** Full test/verification/quality-gate discipline, same as every prior phase.

### Phase 3 — Placement elasticity (the Vespa axis: node count independent of partition count)
Goal: once partition *count* is genuinely dynamic (Phases 0-2), make node *count* changes cheap too — adding a node should absorb some partitions without existing nodes needing to shuffle data among themselves, matching Vespa's "new node steals ~1/n of buckets, nothing moves between old nodes" property rather than Cassandra's "existing nodes reshuffle ranges" property.

- [ ] **3.1** Audit `ServerlessStorageExistingShardsAllocator` (already handles writer/reader placement preferences, cache-locality/cost-model allocation from §10) against Vespa's ideal-state algorithm shape: is placement already close to a deterministic, coordination-free function of `(shardId/ShardRange, nodeId)`, or does it currently require comparing against other nodes' current assignments (which would make it Cassandra-shaped, not Vespa-shaped)?
- [ ] **3.2** If a redesign is warranted, scope it narrowly: this is a placement-preference change, not a new distributed system — core's own `AllocationDecider`/`ShardsAllocator` SPI is almost certainly sufficient, unlike Phases 0-2 which needed new core surface.
- [ ] **3.3** This phase is the least urgent relative to the user's stated goal (which is about shard *count*, not node elasticity specifically) — treat as a genuine "if time permits" phase, not a blocking dependency of the others.

## Part 6: Explicit non-goals (stated honestly, not silently dropped)

- **A DynamoDB-style separately-scalable metadata-lookup service (MemDS-equivalent).** Core's routing indirection is resolved from cluster state, held in memory on every node, exactly like every other piece of `IndexMetadata`. This is consistent with how OpenSearch already works and is *not* being proposed as a new distributed service — that would be a categorically larger project (a new coordination subsystem) than what this plan scopes. This is a real, not-yet-quantified limit: cluster state size and per-update publish cost are known (if not precisely benchmarked here) to grow with shard count, and a `ShardRange[]` array per split index adds to that growth in a way this plan has not measured. Treating "how many partitions can cluster state hold before this becomes a problem" as an open, later question — not a solved one — is the honest position; do not assume it's fine without a real benchmark once Phase 1 automation starts producing many partitions per index in practice.
- **A literal reimplementation of DynamoDB's split-for-heat traffic-shape analysis.** Not confidently documented publicly; Phase 1 uses a simpler, honestly-scoped first cut instead of guessing at an undocumented algorithm.
- **Vespa-style dual sub-DB (ready/not-ready) per-bucket search-vs-store separation.** Out of scope; this plugin's existing writer/reader engine role split already covers a related but different concern (§7.1.2/§10) and conflating the two would be scope creep.
- **Changing classic (non-serverless-storage) OpenSearch shard behavior.** Everything in this plan is scoped to `SERVERLESS_STORAGE_ENABLED_SETTING`-opted-in indices, following the pattern this whole plugin has used throughout — a classic shard should observe zero behavior change from any of this.

## Part 7: Open questions / risks to resolve before or during Phase 0

- **Blast radius of 0.2 (AllocationService wiring)**: this is genuinely core, shared, every-shard-in-the-cluster machinery — the largest blast-radius item in this entire plan, larger than B8's `Engine#onPrimaryTermBumped` hook from this session. Expect this to need the most careful design-then-review cycle of anything here, likely its own short design-approval checkpoint before implementation, consistent with how B8 was handled this session.
- **Does `InPlaceSplitShardRecoverySource`'s existing (if unimplemented) shape actually accommodate a zero-copy, no-bytes-moved recovery**, or does core's recovery framework assume some minimum amount of real I/O happens during any `RecoverySource`-driven recovery (e.g., timing/health-check assumptions tuned for real segment copies)? Needs direct verification in Phase 0.1 before committing to the design in 0.3/0.4.
- **The blob-path identity question in 0.4** (how a child's object-store identity relates to the parent's `<indexUuid>/<shardId>` prefix) is the one piece of this whole plan with no precedent anywhere in core or the plugin — flagged explicitly as needing its own design spike, not a default assumption.
- **Upstream core is actively developing this scaffold.** PRs #20859/#20979/#21120 landed within the last several months; there may be more upstream activity by the time Phase 0 starts. Re-check `git log` for new commits touching `SplitShardsMetadata`/`ShardRange`/`InPlaceSplit*`/`AllocationService` before starting Phase 0.2, to avoid duplicating work upstream may have already done.
- **Cluster-state scale as partition count grows.** Not benchmarked in this plan (see Part 6's non-goals note) — a `ShardRange[]` per split index adds to cluster-state size and per-update publish cost in a way that hasn't been measured. Before Phase 1 automation is allowed to run unattended and produce many partitions per index, get a real number for how cluster-state publish latency degrades as `SplitShardsMetadata`'s child-shard count grows, rather than assuming it scales fine by analogy to today's much lower typical shard counts.
