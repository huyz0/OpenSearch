title: Interoperability
description: How serverless storage interacts with existing OpenSearch features — search, snapshot/restore, kNN, PIT, CCR, remote-backed storage, pull ingestion, and read-write separation.
---

This page states plainly, for each feature, whether it's supported, not supported, or genuinely unknown from the evidence available. Where nothing in the code or design docs settles the question, it's labeled **Unknown** rather than guessed at — a wrong guess here is worse than an honest gap.

## Normal search — ✅ Supported

Close to a non-question: both engines build on core's own engine classes and change almost nothing about how a query actually executes. `ObjectStoreReaderEngine extends ReadOnlyEngine` and `ObjectStoreWriterEngine extends InternalEngine`; neither overrides query execution, aggregation, or sorting. The reader engine's own class javadoc states the design intent directly: once `ObjectStoreCommitMaterializer` has populated the engine's directory with a manifest's files, that directory holds an ordinary valid Lucene commit, and `ReadOnlyEngine` already implements everything a read-only shard needs — search, get, completion stats, segment listing, refusing writes — against exactly that. Only `refresh`/`maybeRefresh`/`acquireSearcherSupplier` are overridden, purely for activity-timestamp bookkeeping. `RestSearchAction` also explicitly declares `ApiAvailabilityScope.AVAILABLE` (see [Core Changes](/core-changes/)), so it isn't blocked by the plugin's REST gate either.

## Snapshot & restore — ✅ Supported, but the snapshot is a pointer, not an independent copy

Real, core-native snapshot support, not the plugin's own narrower in-place mechanism described below. `PUT _snapshot/<repo>` followed by `_snapshot`/`_restore` work against a serverless-storage index through core's real machinery, against any `fs`/`s3`/`azure`/`gcs`/`hdfs` repository. Instead of copying local Lucene commit bytes, `Engine#attemptEngineNativeSnapshot` pins the shard's current manifest generation and hands back an opaque pointer; the repository stores that pointer, not segment files, and restore materializes back from it. See [Snapshot & Restore](/design/snapshot-restore-proposal/) for the full extension point and [Core Changes](/core-changes/) for the exact hooks. The plugin's old blanket rejection of `CreateSnapshotAction` is gone: it would otherwise have blocked this from ever being reached.

**The pointer never contains the data.** Snapshotting to a repository different from wherever this plugin's own storage lives, for example the plugin's data sits in S3 and `_snapshot` targets a GCS repository, does not copy segment bytes into GCS. GCS gets a few hundred bytes: an engine ID and a manifest reference. The bundles stay in S3, and restore always reads them from there, regardless of which repository the snapshot metadata lives in. If S3 becomes unreachable or the data is deleted, the GCS "snapshot" restores nothing: it never held an independent copy. Ordinary remote-backed storage doesn't have this problem by default: a remote-store-enabled index still keeps a full local Lucene commit, so `_snapshot` copies real bytes to the target repository unless the operator explicitly opts into `remote_store_index_shallow_copy` (default `false`) on the repository, which is when core's own snapshot gets this same pointer-only behavior. This plugin has no equivalent opt-out: `attemptEngineNativeSnapshot` never returns empty once configured, so every snapshot of a serverless-storage shard is pointer-based, unconditionally, with no classic byte-copying path available at all.

**Do not conflate this with the plugin's own `_snapshot_pin`/`_snapshot_restore` REST actions** (see [REST API Surface](/design/rest-api/)). Those remain a separate, narrower mechanism: pin the shard's current manifest generation under a name via `DurablePinRegistry`, later CAS the shard head back to that pinned `(primaryTerm, generation)`, all in place, no repository, no data movement. The two exist for different reasons: the REST actions are a lightweight, no-repository restore-in-place primitive built for this plugin's own use; core's `_snapshot`/`_restore` is the mechanism most tooling already expects, portable in the sense of using the standard API surface, not in the sense of the caveat above.

Two more things this path doesn't cover: cross-version/cross-cluster compatibility of the opaque pointer bytes is unaddressed beyond a plain string-equality tag check, so restoring a snapshot into a different plugin build or a different cluster is untested. And restoring a *legacy* (classic, Lucene-commit-based) snapshot *into* a serverless-storage index remains unanalyzed.

## kNN / vector search — ✅ Supported, with a documented scale caveat

No kNN-specific code exists anywhere in the engine classes — vectors are ordinary segment files, following the same path as normal search above. A real benchmark against a Lucene HNSW k-NN index (128-dim vectors, a multi-megabyte `.vec` file spanning several 1 MiB cache blocks) through the `LazyBundleDirectory`/file-cache path found cold k-NN query cost comparable to cold term-query cost (roughly 3.2s vs 3.1s without prefetch), and both drop substantially with boot-set prefetch (k-NN to roughly 355–380ms). This is honestly scoped as one dataset at one scale — the design docs flag that a larger graph with deep, scattered multi-hop traversal per query could still show a gap opening up at production scale that this benchmark didn't reach. No distinct vector-aware cache or graph-aware boot set was built; the evidence gathered didn't justify one.

## Point-in-time (PIT) search contexts — ⚠️ Unknown / documentation gap

Two different things are both informally called "PIT" here and should not be conflated:

- The plugin's own **PITR retention** (`PitrRetentionConfig`, `DurablePinRegistry`) is about *object GC eligibility* — keeping a manifest's bundles alive for a retention window. This is tested directly (a GC test explicitly stands in for "an open PIT" by pinning a generation and confirming its bundle survives concurrent aggressive GC sweeps).
- Core's actual `_search/point_in_time` mechanism pins a `SearcherSupplier`/`DirectoryReader` at the engine level via `ShardSearchContextId`/`ReaderContext`. **No test or design document anywhere in this plugin exercises this specifically.**

Mechanically, `ObjectStoreReaderEngine.acquireSearcherSupplier` just delegates to `ReadOnlyEngine`'s implementation after timestamp bookkeeping, and manifest materialization is purely additive (new files are written; nothing is deleted out from under an already-open reader) with reopen going through Lucene's standard `DirectoryReader.openIfChanged` — which suggests core's PIT context *should* work by the same reader ref-counting Lucene already relies on for any live index. **This is inference from reading the code, not a tested or documented guarantee.** Treat "does manifest-generation advancement stay safe under a long-held core PIT context" as an open question, not a settled one.

## Cross-cluster replication (CCR) — ⚠️ Unknown / out of scope, unaddressed

No code or design-document reference to CCR (`org.opensearch.plugin.replication`, leader/follower index replication) exists anywhere in this plugin. The only "cross-cluster" language present concerns a completely different thing — the plugin's own manifest-import mechanism for granting cross-account/cross-cluster read access to a storage prefix, not CCR itself. This is a genuine gap: nothing states serverless-storage indices are compatible with, incompatible with, or even untested against CCR.

## Remote-backed storage — ⚠️ Partially supported; partially an unavoidable, wasteful prerequisite

This plugin's own durability publication and core's remote-store upload path do similar things, which raises the obvious question of whether they conflict or double up. The plugin's writer engines opt **out** of core's `RemoteStoreRefreshListener` upload path via `EngineFactory#ownsRemoteSegmentDurability()` (see [Core Changes](/core-changes/)) — this plugin's manifest/bundle publication *replaces* remote-store upload for writer shards, rather than layering on top of it.

**However**, `index.number_of_search_replicas` (needed to create reader shards at all) still requires `index.remote_store.enabled: true` as a hard, unconditional core prerequisite — that validation has no serverless-storage-aware carve-out anywhere. The consequence, acknowledged directly in the design docs: a serverless-storage index with `remote_store.enabled: true` likely runs core's own remote segment-store upload machinery pointlessly in the background, alongside this plugin's own publication, since `ObjectStoreWriterEngine`/`ObjectStoreReaderEngine` never reference the remote-store directory core still constructs for them. This was validated with a real multi-node remote-store integration test, which also surfaced and fixed a real bug: the plugin's own rejection of `index.replication.type: SEGMENT` (reasoning: manifest publication already *is* this shard's segment replication mechanism) initially blocked search-only-replica index creation entirely, since core requires `SEGMENT` replication alongside `remote_store.enabled` for search replicas specifically — fixed by scoping the rejection to `index.number_of_replicas > 0` only, leaving search-replica-only indices unaffected.

## Pull-based ingestion — ⚠️ Unhandled, no evidence either way

No writer-engine hook, settings check, or test anywhere in this plugin references OpenSearch's pull/streaming ingestion feature (Kafka-poller-style `IngestionEngine`). The one incidental reference to `IngestionEngine` in the design docs concerns reusing an unrelated existing core seam for a different purpose (WAL/recovery warmup signaling), not integrating pull ingestion itself. Genuinely out of scope / unaddressed — not explicitly rejected, just never built.

## Read-write separation (search replicas) — ✅ Supported, and this plugin reuses a pre-existing core concept rather than inventing one

`ShardRouting.isSearchOnly()` and `index.number_of_search_replicas` are **core's own pre-existing** search-replica routing concept, not something this plugin added. Before this work, a search-only replica still instantiated a full, ordinary writable `InternalEngine` with a full local index — the *routing*-level role existed, but nothing in the *engine* layer differentiated it. This plugin's contribution is exactly that missing piece: giving the pre-existing `isSearchOnly()` role a genuinely different, lazily-materialized `ObjectStoreReaderEngine` via `ReaderEngineFactory`, made possible by the per-shard-role `EnginePlugin` dispatch seam documented on [Core Changes](/core-changes/). In short — core already had the writer/reader *routing* split; this plugin adds the matching *engine-layer* split that routing split was previously unable to express.
